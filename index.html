Q
项目管理分为哪七个阶段？每个阶段具体怎么做？
必考 ⚠️

参照CMMI标准，项目划分为 七个阶段（项目计划与监控贯穿全程）：

① 项目立项 （产品类由产品经理作为项目经理组织立项，其他类由项目经理或运维主管组织立项）

第1步 · 项目评估

  • 建设内容分析（项目经理牵头，与产品经理、技术组长共同拆解）：依据《项目可研报告》《项目招标文件》《项目投标文件》《项目合同》，评估管理/设计/研发/测试/部署/运维/采购/差旅等成本，识别风险 → 《项目研发成本及风险预估表》（项目经理负责）
  • 整体计划制定（项目经理）：根据工期+人员情况 → 《项目整体实施计划》（项目经理负责）
  • 立项评审（项目经理）：编写《项目立项汇报PPT》（项目经理编写），向职能负责人+公司领导汇报内容/成本/团队/计划/风险，征求意见修改

第2步 · 立项审批

  • 编写《项目立项申请表》（项目经理编写），连同预估表+计划表提交PMO检查材料
  • PMO确认无误后 → 在OA上发起立项流程 → 项目管理委员会审批 → 正式立项

第3步 · 项目启动

  • 在立项汇报PPT基础上调整 → 《项目启动会PPT》（项目经理调整）
  • 组织全体项目成员参加启动会 → 明确建设内容/人员职责/里程碑/日常工作制度
  • 根据软件系统 → 《系统迭代计划》（项目经理制定并录入系统）
📋 归档材料清单（10项）：
项目可研报告项目经理·可选
项目招标文件项目经理·招标类必须
项目投标文件项目经理·招标类必须
项目合同项目经理·产品和内部项目外必须
项目立项汇报PPT项目经理·必须（纯产品实施可裁剪）
项目研发成本及风险预估表项目经理·必须
项目整体实施计划项目经理·必须
项目立项申请表项目经理·必须
项目启动会PPT项目经理·必须
系统迭代计划项目经理·必须

② 需求分析 （产品经理组织，项目经理协调资源）

第1步 · 需求调研

  • 制定《需求调研计划》（产品经理制定） + 准备《需求调研材料》 → 开展调研
  • 汇总分析（业务场景/流程/角色/数据标准/功能要点）→ 编写《业务需求说明书》（产品经理）
  • 产品组内审核 + 客户确认 → 签订《需求确认单》（产品经理/项目经理）

第2步 · 功能设计

  • 系统功能架构设计 → 分解子系统/模块/功能 → 《系统功能清单》（产品经理）
  • 复杂功能绘制《系统原型》（产品经理） + 注释说明，重难点标注
  • 产品组内预审（产品组负责人审核）→ 修改 → 确保功能齐全/设计合理/逻辑通畅/原型规范

第3步 · 需求评审

  • 产品经理提前一天发邮件+工作群通知 → 全体成员参加
  • 逐项提出评审意见 → 产品经理记录在功能清单 → 整改
  • 视改动范围重新评审或小范围通知 → 所有问题点处理完成 + 提出人签字确认
  • 项目经理填写《需求评审单》（项目经理填写） + 附本次通过的功能清单

第4步 · 需求录入

  • 技术组长评估研发工作量填入功能清单
  • 产品经理将功能点录入项目管理系统（禅道），功能点数量/名称必须与清单完全一致
  • 评审完后2天内完成录入
📋 归档材料清单（8项）：
需求调研计划产品经理·可选
需求调研材料产品经理·必须
业务需求说明书产品经理·必须
系统功能清单产品经理·必须
系统原型产品经理·复杂功能必须
需求规格说明书产品经理·可后补
其他备用材料产品经理·可选
需求评审单项目经理·必须

③ 设计开发 （研发组主导，产品经理参与评审+周验证）

第1步 · 程序设计

  • 技术组长输出《技术总体设计说明》（技术组长）（框架/中间件/加密机制），同时遵循《系统编码规范》《界面设计规范》（技术组长提前制定）
  • 按功能点逐项详细设计 → 《系统详细设计说明》（技术组长组织开发人员）；《数据库设计说明》（技术组长，结项时必须）
  • 研发组内预审（技术组长审核）→ 整改 → 确保功能齐全/设计完整/逻辑正确

第2步 · 设计评审（仅重难点功能）

  • 技术组长提前一天通知 → PM记录意见在功能清单 → 整改→签字确认→《设计评审单》（项目经理填写）

第3步 · 用例编写（与程序设计同步，不晚于1周内）

  • 测试工程师按需求+功能清单+原型编写《测试用例》（测试工程师） → 测试组内预审 → 用例评审→《测试评审单》（项目经理填写）

第4步 · 程序开发

  • 技术组长创建开发任务分配 → 开发编码+自测 → 系统标记完成
  • 产品经理每周检查开发完成功能，按测试用例验证 → 通过则转测试，不符合则打回
  • 有对外接口 → 输出《对外接口调用说明》
📋 归档材料清单（11项）：
系统编码规范技术组长·必须
界面设计规范技术组长·必须
技术总体设计说明技术组长·必须
系统详细设计说明技术组长·必须
测试用例测试工程师·必须
数据库设计说明技术组长·结项时必须
对外接口调用说明技术组长·有对外接口必须
内部接口说明技术组长·有前后端交互必须
外部接口调用说明技术组长·有调用外部接口必须
设计评审单项目经理·必须
测试评审单项目经理·必须

④ 系统测试 （内部测试+用户测试）

内部测试（技术组长主导）

  • 技术组长填写《项目测试申请单》（技术组长） → 邮件提测
  • 测试工程师输出《内部测试环境部署方案》
  • 测试工程师搭建环境 → 按测试用例功能/性能/安全测试 → BUG录入禅道
  • 输出《功能测试报告》《性能测试报告》《安全测试报告》（测试工程师）

用户测试（产品类由产品经理主导/其他项目由项目经理主导）

  • 确认测试功能 → 整理参数配置 → 项目经理组织输出《用户测试环境部署方案》 → 搭建用户测试环境 → 产品经理编制内部培训材料 → 内部培训后输出《内部培训签到表》（产品经理） → 项目经理组织用户培训后输出《用户培训签到表》（项目经理） → 组织测试 → 问题记录到《项目问题跟踪表》《问题反馈单》
📋 归档材料清单（9项）：
测试申请单技术组长·必须
功能测试报告测试工程师·必须
性能测试报告测试工程师·有性能测试点必须
安全测试报告测试工程师·必须
内部测试环境部署方案测试工程师·必须
用户测试环境部署方案项目经理·必须
内部培训签到表产品经理·必须
用户培训签到表项目经理·必须
问题反馈单项目经理·有BUG或需求时提交

⑤ 部署上线 （先确认环境+申请，再部署）

第1步 · 环境准备

  • 产品经理整理上线材料：《子系统清单》《系统模块清单》《系统功能清单》《系统权限清单》《系统配置文档》
  • 项目经理编写《系统部署方案》（项目经理）（含网络拓扑）→ 评审 → 《部署方案评审单》（项目经理）
  • 准备中间件+应用程序包+安装手册 → 项目经理填写《上线申请单》（项目经理）（客户签字确认）；同时准备《发布程序包》（测试工程师提供）、《中间件安装手册》《应用程序安装手册》（运维工程师）、《测试数据库》《数据库升级脚本》

第2步 · 部署发布

  • 按部署手册部署 → 验证主要功能 → 输出《服务部署清单》《服务配置说明》

系统功能清单产品经理·必须
系统权限清单产品经理·必须

⑥ 验收结项

第1步 · 项目验收

  • 项目经理组织补充后补文档（需求规格/详细设计/数据库设计等）→ 整理验收文档 → 开验收会 → 获取《项目验收单》（项目经理负责推动）

第2步 · 项目结项（原则上先拿验收单再结项）

  • 项目经理组织交接会向运维团队介绍 → 项目管理委员会审核交接材料 → 《项目交接单》（项目经理）
  • 项目经理填写《项目结项单》（项目经理） → PMO审查归档材料完整性 → 公司领导审批结项
📋 归档材料（结项包含全流程材料，见附表A）：

《项目交接单》项目经理·交接会→委员会审核

  • 项目巡检（服务器/中间件/应用程序/业务功能/业务数据）（运维人员）→ 《项目巡检记录》
  • 问题处理（记录问题+客户需求 → 排期处理，配合第三方测评）（项目经理/运维人员）

Q
团队由哪些职能组组成？产品经理在哪个组？
管理制度

项目团队由 四个职能组 组成：

  • 项目管理委员会：公司领导、职能组负责人、PMO — 审批立项/变更/结项
  • 项目交付组：项目经理、运维主管、运维工程师 — 过程管控、部署上线、运维
  • 产品组（← 产品经理在此）：需求分析、功能验证、内部培训
  • 研发组：技术组长、开发工程师、测试主管、测试工程师 — 设计开发、测试
Q
公司的四条「管理红线」是什么？
必考 ⚠️

⛔ 四条红线（触碰即事故）

  • 私自动工 — 未经项目管理委员会或公司领导批准提前投入开发；客户提出合同外需求，未及时汇报公司领导和商务，私自投入开发
  • 私交代码 — 客户要求提交项目源代码，未及时汇报公司，私下将源代码提交客户
  • 数据安全 — 长时间私自留存客户重要数据，出现数据安全问题被公司巡查发现或被客户发现通报的
  • 质量事故 — 由于系统代码质量或部署原因，出现生产服务故障导致业务无法经办，被公司巡查发现或被客户发现通报的
Q
产品经理有哪些核心岗位职责？
必考 ⚠️

根据《软件交付部核心岗位职责》，产品经理职责分为四大块：

1. 新产品预研

  • 按公司业务发展策略，负责现有产品线或新方向的市场需求调研、业务功能分析
  • 组织新产品关键技术可行性预研
  • 评估投入成本和产出利润 → 形成整体的可行性分析报告

2. 产品研发管理（全流程管控）

  • 产品规划和立项：业务需求分析→功能模块规划→核心功能原型设计→组织研发评估工期/工作量→编写立项材料
  • 过程管控：整体计划制定、团队人员管理、里程碑节点管控。以周为节点对偏差（里程碑/研发进度/产品成本）制定风险防范和应对措施
  • 需求输出和管控：功能详细设计→需求材料→组织需求评审→以周为节点对功能开发情况进行验证→研发过程中的新需求和问题记录处理→协调调整开发和测试计划
  • 成果物输出和审查：编写管理材料/需求材料/培训材料/产品介绍材料，并按照公司标准审查其他团队成员输出的开发设计材料、测试材料、部署实施材料，组织整改
  • 产品发布和结项：准备演示环境和数据→召开产品发布会→归档→发起结项
  • 产品维护管理：记录产品缺陷和需求→影响用户使用的问题安排修复→更新产品资料

3. 项目售前支撑

  • 协助售前进行客户沟通汇报、项目需求调研、方案规划、研发和实施成本评估，输出相关文档

4. 项目实施支持

  • 项目需求输出和管控：参与需求调研→系统功能详细设计→需求材料输出→组织需求评审→每周功能验证→记录处理新需求和问题
  • 项目文档输出和评审：输出需求材料/培训材料，参与开发设计、系统测试、实施部署等环节的评审，提出问题和整改意见
  • 项目内部培训：面向项目团队成员提供系统操作培训，必要时按项目经理安排参与客户培训
  • 系统问题记录和跟踪：以周为节点汇总各项目问题处理情况，对需要产品参与的问题提供解决方案支撑
💡 考核注意：产品经理不只管需求，还要审查开发设计/测试/部署文档，并且参与全流程评审（需求/设计/测试/部署）。这是容易漏答的部分。
Q
PMO 的主要职责是什么？
岗位职责

PMO（项目管理办公室）职责分为四大块：

  • 流程规范化管理 — 审核、发布、归档项目流程规范，建立培训体系，不定期进行培训和考核
  • 实施流程审查 — 审查项目立项/变更/结项流程及相关材料，符合标准后再流转
  • 过程监管 — 监督里程碑节点完成情况和成果物检查；收集汇总绩效指标（计划制定/节点管理/成本管理/研发进度/风险识别及应对）
  • 项目集日常管理：
    • 在湖楚系统、SVN、禅道中创建和维护项目信息，分配用户权限
    • 组织项目周例会，记录问题和任务并跟踪完成情况
    • 汇总整合周报、月报及过程信息数据
    • 系统版本发布：项目经理邮件通知某项目版本发布后，在项目发布栏进行版本发布；每周检查里程碑完成情况

紧急问题怎么处理？和常规问题流程有什么区别？
实操重点

🚨 紧急问题处理流程

时间有限时 → 可同步开展需求分析、设计开发等工作
→ 事后在指定时间内补全过程文档
→ 如果紧急到需要立即处理和发版且连正规测试流程都来不及 → 邮件上报公司领导获得批准

⑤开发进度 每周功能完成情况 产品验证未通过 / 功能延期
⑥总体成本 已用成本 vs 计划成本 已用 > 计划

系统提测和发版的流程区别？

Q
迭代计划中未完成的里程碑节点怎么调整？
操作指引

调整规范：

  • 本周有未完成的里程碑节点，且无法通过加班完成的 → 可调整迭代计划
  • 形成2.0或更高版本的迭代计划
  • 项目经理发邮件给上级领导和PMO，回复通过后在禅道上变更
  • 调整后需要在下周之前完成
✅ 注意：理由合理且不影响客户交付的，准许计划变更，不会计入绩效扣分。

Q
需求评审复现讲解的标准步骤是什么？（考核日核心流程）
🏁 考核核心

🎯 考核日现场复现 — 五步法

第1步 · 背景说明

这个功能解决什么业务问题？用户是谁？在什么场景下使用？

第2步 · 功能逻辑

功能的核心逻辑是什么？输入→处理→输出 是什么？涉及哪些业务规则/数据校验？

第3步 · 交互流程

用户操作路径：从哪进→看到什么→操作什么→到哪去。对照原型逐页讲。

第4步 · 边界情况

异常数据、权限控制、超时处理、空状态、并发冲突等边界条件怎么处理？

第5步 · 回答提问

评委（领导/同事）提问 — 回答要站在业务价值和用户体验角度

💡 备战建议：选3-5个核心功能点，每个功能点按上面五步法写逐字稿演练。
Q
如何理解「功能清单」的完整结构？
🏁 考核核心

功能清单按 子系统 → 模块 → 功能点 三级结构组织：

系统名称（如：公共服务事项系统）
├── 子系统A（如：事项管理）
│ ├── 模块A.1（如：事项录入）
│ │ ├── 功能点A.1.1（如：新增事项）
│ │ ├── 功能点A.1.2（如：编辑事项）
│ │ └── 功能点A.1.3（如：删除事项）
│ └── 模块A.2（如：事项审批）
│ ├── 功能点A.2.1（如：审批流程）
│ └── 功能点A.2.2（如：审批意见）
└── 子系统B ...

标注信息：每个功能点需标注优先级、开发状态、是否涉及性能测试。

⭐ 能对着功能清单不看原型，说出每个功能点做什么、为什么做、怎么做。

Q
系统版本号的三位数字各代表什么含义？
文档标准

系统版本号为 三位：X.Y.Z

位变化条件示例
X（主版本） 系统框架重构 或 产品版本升级 1.0.0 → 2.0.0
Y（次版本） 新功能增加 或 原有需求调整 1.0.0 → 1.1.0
Z（修订号） 仅做BUG修复 1.0.0 → 1.0.1

第一版上线后为 1.0.0。

📌 文档版本号 vs 系统版本号：文档版本号两位（0.1→1.0→1.1→2.0），系统版本号三位（1.0.0→1.1.0→1.0.1），两者不同，不要混淆。
